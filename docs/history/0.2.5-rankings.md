## 35. The 排行 tab of the local statistics page

### 35.1 Rankings over the stored matches — `ui/stats.js`, `screens/stats.js`, `css/screens/stats.css`, `public/i18n/*.json`, `test/ui/stats.test.js`

**Seen.** The statistics page (§27.55, the 本机数据 recorded in `localStorage['sp.pref.stats']`) gains a fifth tab, 排行,
with four sections:

| 分区 | 指标 | 口径 |
|---|---|---|
| 分组胜率 | 地图 / 首领 / 隐秘核心首领 / 羁绊 | 按 id 分组，`wins / games` |
| 惯用阵容 | 干员 Top 5、羁绊 Top 5 | 干员按出现次数；羁绊按**激活**局数 |
| 羁绊最高层数 | 每个 `bondId` 的 `layers` 最大值 | 附达成时间 |
| 战斗均值 | 局平均伤害、局平均领袖伤害 | 后者只统计 `roundsPassed ≥ LATE_GAME_ROUND`（13） |

总览 additionally gains a 隐藏阶段胜率 card next to the existing 到达 / 通关隐秘核心 counts.

**Counting rule.** Every ranking reads the same set the existing aggregates do — `countsTowardStats` (§27.55): a settled
record always counts, a quit record once the player had cleared a round or was already eliminated. 胜率 uses
`selfWon` (the self row's `victory`, i.e. **team won AND still in at the end**, `match/results.js buildResult`), not the
team-level `rec.victory` — switching would make the same player's win rate disagree with the 胜/负 shown in 对局记录.

**Grouped win rates.** `stageId` / `bossId` / `hiddenBossId` come straight off the record frame; a bond's group key is
`bonds[].bondId` and only `active: true` entries count as 激活 — `layers > 0` without activation is not "used". The
**hidden boss gets its own table**: only a match that reached 隐秘核心 carries `hiddenBossId`, so folding it into the main
表 would dilute that table's denominator.

**Why 领袖伤害 filters on the round, not on 盟约 layers.** The request said 「层数 ≥ 13」, which in this project normally
means 盟约叠层 (`activatedLayers`). We read it as **回合数** (`roundsPassed`) instead: 领袖伤害 is produced almost entirely
in round 14's 最终攻势, so a round threshold is what makes the mean comparable, whereas "13 layers" has no mechanism
attached to it and would import the same survivorship bias the bond tables already have. **[ASSUMED]** — the maintainer may
switch it; it is one `rounds >= LATE_GAME_ROUND` comparison in `aggregateStats`, and the constant is exported.

**Why the averages carry their own sample count.** A quit record has no `stats` block (`buildQuitRecord` never writes one)
and an imported or compacted row may hold neither `lineup` nor `bonds`. So each average keeps `{ sum, n }` and the page
prints `n` — the denominator is "records that have this number", never `count`.

**Determinism of the order.** `rankByRate` / `rankEntries` sort by the primary key descending, the secondary key
descending, then **the id ascending**. The previous tables leaned on `Array#sort` stability, which makes the order of tied
rows depend on input order — after an import merge the same data could rank differently. `takeTop` keeps **every entry tied
at the cut** (a 6th operator level with the 5th produces a 6th row) rather than silently dropping one.

**Small samples.** Groups below the 最少局数 filter are moved **behind** the qualifying ones, never hidden: a map played
once and won shows 100%, which misleads, but hiding it makes the user think the data went missing. The filter defaults to 1
(no filtering) and is a chip row on the page; the row count is always visible next to the rate.

**Bonds and compactions — the storage change.** Before this change `compactRecord` kept only the frame and the self
row's summary, dropping `lineup` and `bonds`; §27.55 said so outright ("only the newest `FULL_KEEP` 30 records keep their
rows"). Every lineup-derived ranking would therefore have been capped at the newest 30 matches. `compactRecord` now keeps a
**slim** copy: an operator's `id` (plus `kind`, so summons stay distinguishable) and a bond's `bondId` / `layers` / `active`.
Tile position, items, `golden`, `diy` and `standInFor` remain replay-only and are dropped. **No `STATS_VERSION` bump** —
the record shape is unchanged, `normalizeRecord` already accepts those fields; only what a compaction writes changed.

The cost is measured, not guessed (`tools/…` probe over the same generator the storage test uses — a full board and every
bond slot is the heavy end):

| 规模 | 每条 compact 后 | 800 000 字符预算下能留 |
|---|---|---|
| 单人 6 干员 / 5 羁绊 | — | 746 局 |
| **单人 8 干员 / 6 羁绊（典型）** | — | **674 局** |
| 单人 12 干员 / 12 羁绊 | — | 490 局 |
| 双人 8 干员 / 6 羁绊 | — | 634 局 |
| 四人满配 10 干员 / 12 羁绊 | — | 389 局 |

This **supersedes the "974 fit" figure** measured for the 0.2.2 compaction in §27.55: `fitToBudget` still trims to the
budget automatically (nothing overflows — the quota failure path is unchanged), it just retains fewer matches. The two
storage tests in `test/ui/stats.test.js` were updated for the new behaviour and name the numbers above.

**Coverage is reported, not assumed.** Records written *before* this change already lost their lineup when they were
compacted, and cannot be recovered. `aggregateStats` therefore counts how many records actually carried a lineup / bond
list (`coverage.lineup` / `coverage.bonds`) and the page prints it. The test that distinguishes the two cases is
deliberate: the check is **"is the array non-empty"**, not `rec.compact` — a record compacted after this change has a lineup and
is also `compact: true`, so testing the flag would skip exactly the records the rankings need.

**Data loading.** The tab needs `stages` / `bosses` / `bonds` / `chess` to resolve names and icons (`makeLookups`), where
the overview deliberately reads `config` / `bands` / `assets` only — §27.55's defect (1) was a `<StatsHost/>` that pulled
every game data file at mount. The four files are requested when the tab is first shown, not when the page opens.

### 35.2 不叠层的盟约不进叠层类排行

**不叠层的盟约不进叠层类排行。** `bonds.json` 给每条盟约标了 `noStack`：独行 / 调和 /
协防干员 / 绝技 这四条在游戏机制上**不叠层**，游戏自己也不显示它们的层数（结果页注释原话：
"layers the game never shows"）。所以对它们而言 `layers` 是个没有机制含义的副产品 ——
留在「羁绊最高层数」里就是在展示假数字（实测截图里出现 独行 10、调和 2 这种值），
留在「惯用羁绊」里则会显示一个同样无意义的「平均 N 层」。

判定读 `noStack` 字段而不是比中文名：名字是显示文案（会随语言和上游改动变），`noStack` 才是机制，
而且上游以后新增不叠层的盟约时会自动生效。过滤收敛在一个导出的纯函数 `withoutNoStack(entries, bondOf)`
里，两处调用同一个实现，避免口径漂移。

两处细节：

- **过滤发生在 `takeTop` 之前**，所以「惯用羁绊」是**递补**的 —— 剔掉一个之后第 6 名补上来，
  榜单仍是 5 条。这个榜的语义是「你最常用的 5 个盟约」，让下一个补位才对得上。
- **「分组胜率」里的羁绊表不动**：那统计的是胜负，`noStack` 不影响「这局激活了炎而且赢了」。

**Tests.** `test/ui/stats.test.js` gains a `排行` suite (11 cases): the id-grouped win rates and the missing-id case, the
summon exclusion and the same-operator-twice counting, the bond activation vs `maxLayers` split, the average denominators,
the `LATE_GAME_ROUND` boundary, coverage, and the three ordering helpers. `node --test test/ui/stats.test.js` 60/60;
`node tools/i18n.mjs check --all --strict` 1214/1214 in all four packs; `eslint` clean on the touched files.

### 35.3 账号系统与全服排行榜

本机统计（上面的 35.1 / 35.2）只看得见**这个浏览器**里的对局。这一节加的是它的另一半：
一份服务端的账号，以及按账号记账的全服榜单。

**账号（server/accounts.js）。** 用户名 + 服务端签发的设备凭证 + 可选密码。三条设计：

- **身份只由服务端裁定**：`accountId` 是 CSPRNG 生成的 `a_` + 16 字节 hex，客户端从不自报
  （沿用 server/net.js 已有的做法 —— `playerId` 也是服务端发的）。客户端在 hello 里塞 `accountId`
  或别人的凭证都不会起作用，`test/accounts-handshake.test.js` 有一条用例专门钉这个。
- **用户名不能当密码**：名字要显示在榜上，所以是公开的；它只用来「找」账号，进得来要靠凭证或密码。
  名字一旦被占用，没有凭证/密码的人**根本进不来**（`NAME_TAKEN`）—— 这是防串号那条线。
- **accountId 与显示名分离**：改名不换 id，历史成绩不会分裂，也没人靠改名占别人的过去。

凭证只存 `sha256`（文件被读走也不能直接登录），密码用 scrypt，登录失败一律返回同一个错误
（不泄漏用户名是否存在）。用户名规范化做 NFKC + trim + 折叠空白 + 小写，挡掉 `PenHu` / `penhu` /
`ＰｅｎＨｕ` 这类等价写法。存储是原子的（临时文件 → fsync → rename），**加载失败时拒绝启动**
而不是当作空库 —— 与 globals 那一套纪律一致。

一个账号可以有**多个**设备凭证（上限 8，超出淘汰最旧的）：只在第二台设备上用密码登录时，
第一台不该被踢下线。

**握手（server/net.js）。** `hello` 多了两个可选字段 `accountToken` / `accountPassword`；
`welcome` 用 `accountId` 回话，并在**新签发**凭证时带 `accountToken`（+ 首次的 `accountNew`）。
两处要点：

- 认证只在**新建 session** 时发生。恢复已有 session 时身份早定了，再拿客户端这次带来的东西重新判定，
  就是一个「重连即换人」的口子。
- 名字以**账号**为准：带了有效凭证时，客户端在代号输入框里填什么都不能改变他是谁。

**全服排行榜（server/leaderboard.js）。** 服务端在**自己结算完**时写一笔（lobby 的 onMatchEnd），
不是让客户端上报：

- **谁参加了**只来自服务端座位表（`room.seats → playerId → session.accountId`），
  客户端报什么都不参与；**哪些对局存在**也来自服务端（一份 `matchId` 账本，幂等）。
  两者合起来，客户端造不出一局不存在的对局，也不可能把成绩塞给别人。
- 唯一的信任缺口是「一局内的数值」（伤害 / 叠层 / 干员）—— 那些本来就在浏览器里算（DESIGN §14），
  服务端要复算得开 `SP_VERIFY=all`。这一版**接受上报值**，只做数值合理性钳制（负数 / NaN / 荒谬上限），
  那挡的是程序 bug，不是作弊。页面底部如实写明这一点。
- 指标口径与 35.1 对齐（包括「局平均首领伤害只算 ≥ 13 回合」）。
- 读接口只有一个：`GET /leaderboard`，返回聚合后的榜单，**没有**「按 id 查任意玩家明细」的入口。

**开关与存储位置。** 账号与榜单只在设了 `SP_ACCOUNTS_FILE` / `SP_LEADERBOARD_FILE` 时才启用
（不设 == 行为与加它们之前完全一致，所以 74 个调用 `startServer` 的测试一个都不用改）。
两个文件刻意放在**游戏目录之外**（compose 里挂 `./data:/data`）：deploy.sh 的 rsync 带 `--delete`，
放在游戏目录里会被当成垃圾删掉。

**Tests.** `test/accounts.test.js`（32）、`test/accounts-handshake.test.js`（14）、
`test/leaderboard.test.js`（25）。重点都不是「功能跑通」而是不变量：占用即拒、拿文件也登不进、
同一 `matchId` 只入账一次、没账号 / 是 AI 的不入榜、数值钳制、并列时排序确定、损坏拒绝启动。

### 35.4 没设过密码的账号不会卡死（2026-10-13 上线当天修的）

**症状**：账号没设过密码、浏览器凭证又丢了（清了缓存 / 换设备）时，进不去，
提示「密码不正确」，输多少次都不对 —— 而那个密码根本不存在。

**根因是一次设计疏漏**：`authenticate()` 把「密码错」和「没设密码」都映射成
`BAD_CREDENTIALS`，前端只能显示「密码不正确」。这两件事要分开：
「密码错」重试有意义，「没设密码」重试永远没有意义。

**修法**：新增 `NO_PASSWORD` 错误码，只在「名字命中一个已存在的、且该账号没设密码」时返回。
前端收到它就**收起密码框**（不再诱导重试），换成一条讲清处境的提示 + 一个
「换一个代号」按钮，并且**清掉本地凭证**（`identity.forgetAccount()` + `net.clearPassword()`
+ `net.clearError()`）让玩家能真的从头开始。

**为什么这没有削弱防串号**：唯一能进别人账号的路径始终是「持有服务端签发的凭证」或
「知道密码」，两条都没动；`NO_PASSWORD` 这条路径上不签发 session、不给 accountId、
不发凭证。顺带澄清一个容易想错的地方：**账号存在性本来就能被区分** —— 一个没人用的
名字加合法长度的密码就是注册成功（进得去），一个被占用的名字加密码则是拒绝。
这是「打开就玩」这个设计固有的，不是 `NO_PASSWORD` 引入的。

**顺带修的一个真 bug**：`TextField` 组件根本没有 `type` 参数，标题画面传的
`type="password"` 被静默丢弃 —— 密码是**明文显示在屏幕上的**。给它补上 `type`
（并让 `autocomplete` 在密码框上变成 `current-password`）。这条与错误码无关，
但既然密码框是这个修复的主角，就一起处理了。

**Tests.** accounts 36（原32 +4）、握手 14（改写1 条：断言改为「拒绝时不签发 session /
不回 accountId / 不发凭证」）、leaderboard 25、相关面回归 172/172。

### 35.5 实时在线房间列表（2026-10-13）

**加的是什么。** 大厅画面（`screens/lobby.js`）新增第 04 区「在线同盟」：一行一个在线房间 ——
房间码、房主显示名、模式、难度、人数（博士 / AI / 观战）、等待中 / 对局中，行尾直接
「加入」/「观战」按钮。两条入口（输同盟密钥、点列表）走的是同一对协议消息
（`room.join` / `room.spectate`），没有第二条加入路径要维护。

**实时 = 服务端推送，不是轮询。** 新 S2C `lobby.rooms`（`server/lobby.js roomList` / `broadcastRooms`）：
每帧都是**全量快照**，房间一有变化（创建 / 加入 / AI 补位 / 踢人 / 开打 / 打完 / 解散）就推给所有
**不在房间里**的会话 —— 成员看 `room.state`，两套信息不重复发。推送只挂在 `broadcastState` 和
`disposeRoom` 两个点上：所有会改变行内容的路径都经过它们，不必逐个调用点补丁。`welcome.rooms`
带一份初始快照（重连 / 新标签页不用干等下一次房间变化）。客户端 `store.roomList` 每帧直接覆盖，
没有增量协议要维护。

**行里有什么、没有什么。** 只有 `code / mode / difficulty / inMatch / humans / bots / spectators / host` ——
**没有玩家 id、没有座位明细**：这是「有哪些房间可以进」的目录，不是房间内部状态（座位表只发成员）。
独立模拟房间也列出来（显示谁在线），但没有加入按钮。房间码本身公开：这个服本来就是
「知道地址的人都能进」（§35.3 的口径），列表只是把「等朋友报密钥」变成「点一下」。

**i18n.** 5 条新文案（`在线同盟` / `暂无在线房间` / `对局中` / `房主：{name}` / `加入`）× 4 语言包，
复用已有的 `等待中` / `观战` / `观战席` / 模式与难度名。

**Tests.** `test/room-list.test.js`（7，服务端）+ `test/ui/room-list.test.js`（2，行逻辑与文案）：
S2C 白名单、welcome 快照（空表也是数组）、行形状（多一列就是泄漏了房间内部状态）、成员不收推送、
AI / 开打 / 打完的行变化、解散时空表也推给刚离开的人、多房间按创建时间排序；
行操作纯逻辑 `roomRowActions`（独立模拟不可进、对局中走观战席、满员不可加）与
「两条入口同一条协议」的源码断言。测试之间手动清场 —— 断线的房间要等 60 s 宽限才消失，
不清场会污染下一个测试的列表断言。

### 35.6 给现有账号设置密码（2026-10-13）

**补的是什么死角。** §35.3 的账号系统里，密码是「换设备 / 清了浏览器数据后找回账号」的备用钥匙，
但**只有注册时能设**：先注册了没设密码的玩家，一旦丢了设备凭证就走进 §35.4 的 `NO_PASSWORD`
死角 —— 界面上没有任何办法给已存在的账号补一把钥匙，只能管理员释放名字（丢成绩）。

**入口。** 标题画面在「换设备了？用密码登录」下面多一行「设置密码 / 修改密码」，**只对已经带着
账号在线的会话出现**（welcome.accountId，服务端说有账号才有）：展开后输两遍密码
（本地拦「两次不一致」和「< 6 位」，与服务端 `BAD_PASSWORD` 同一口径），成功后就地把
按钮换成「修改密码」。

**协议与安全口径。** 新 C2S `account.setPassword { password }`，在 **net 层**处理（账号属于会话
身份，不属于房间）。三条不变量：

- **身份只看 `session.accountId`**（服务端从凭证 / 密码裁定出来的）—— 消息里不接受名字或 id，
  这条消息永远改的是「你自己」的账号，不存在「改别人的密码」这条路；
- **设 / 改密码不动任何设备凭证**：在新设备上补了密码，老设备不该被踢下线（§35.3 多设备凭证的
  口径不变）；
- 被拒的短密码**不落库**（`BAD_PASSWORD` 之后账号保持原样，不是"先写进去再报错"）。

welcome 多带 `accountHasPassword`（与 `accountId` 同口径：只在启用账号系统时出现），前端据此
显示「设置」还是「修改」。

**Tests.** `test/account-set-password.test.js`（6，走 onFrame 全消息路径）+
`test/ui/account-set-password.test.js`（3）：注册后补设 →「代号 + 密码」换发凭证、
`welcome.accountHasPassword` 的 false → true、短密码不落库、改密码后旧密码失效新密码生效、
设备凭证不被撤销、没账号 / 没 hello 的连接改不了密码。

### 35.7 密码重置：服主批准的一次性码（2026-10-19）

**补的是什么死角。** §35.6 让「先注册、没设密码」的账号有了补救入口，但反过来还有一条死路：
**设了密码却忘了，而且设备凭证也没了**（换了电脑、清了浏览器数据）。那时账号名还占着，密码想不起来，
凭证又不在这台设备上 —— 原来只能 `release-account.py` 删号，成绩一起没。

**为什么不自己发一封邮件就完事。** 这游戏没有邮箱，也没有可靠的"这个人就是这个人"的凭证 —— 除了
设备凭证和密码本身。所以「重置」必须有一个**外部的人**点头，那个人就是服主。整个流程刻意做成
两段式，让**玩家手里的东西**和**服主的判断**各管一半：

1. 玩家在标题画面「忘记密码」里填代号 → `POST /account/reset-request` → 服务端发一个 8 位重置码
   （字母表去掉 `0/O/1/I` 这些抄错就废掉的字符；库里**只存 `sha256(code)`**，码本身只回给申请者一次）。
2. 玩家把码报给服主（群里、私聊都行）；服主在服务器上批准：

   ```bash
   # 先看有什么待批（名字与时间；码只在玩家手里，所以列表里没有码）
   ssh penhu@100.64.242.120 \
     "curl -s -H 'x-admin-token: $SP_ADMIN_TOKEN' http://127.0.0.1:3000/admin/resets"

   # 按玩家报的码批准（也可以 {"name":"代号"} 按名字批准）
   ssh penhu@100.64.242.120 \
     "curl -s -H 'x-admin-token: $SP_ADMIN_TOKEN' -H 'Content-Type: application/json' \
        -X POST -d '{\"code\":\"玩家的码\"}' http://127.0.0.1:3000/admin/resets/approve"
   ```

   部署要点：`SP_ADMIN_TOKEN` 必须设在 `docker-compose.yml` 的 `stronghold-game` 环境里
   （建议 `openssl rand -hex 16`），**不设就没有 `/admin/*`**（404），游戏其余部分不受影响。
3. 玩家回到「忘记密码」填**同一个码 + 新密码** → `POST /account/reset-complete` → 服务端**撤销该账号
   全部旧设备凭证**、签发一张新凭证，客户端存下来即可正常 hello。

**为什么批准接口只在回环上。** 公网流量是经 frpc 容器（私网地址）进到游戏容器的，`isLocalIp`
那种"回环或私网"的判断在这里**不够** —— 必须严格回环（`127.0.0.1` / `::1`）并且带
`SP_ADMIN_TOKEN`，所以玩家和公网都摸不到 `/admin/*`；没配 token 时这个路径直接返回 404，
不承认自己存在。批准动作本身也只在**服务器本机的 `curl`** 场景下发生，跟 SSH 的信任边界一致。

**不变量**（都写进了 `test/account-reset.test.js`）：

- **申请不验证身份，批准才是闸**：谁都能为任何代号申请（否则先要证明身份，又回到没凭证的死路）；
  没批准的码一步也走不动（`RESET_PENDING`）；批准前连"码对不对"都不回答（同一个码错也报 `RESET_PENDING`）。
- **码只存哈希**：`accounts.json` 里搜不到明文码；重放同一个码报 `RESET_BAD_CODE`（完成后记录被清掉）。
- **重新申请覆盖旧码**：同一账号不会同时有两个有效申请，旧码立刻作废。
- **完成即全撤旧凭证**：重置的典型场景就是"号可能被别人上了"，留着旧凭证等于留着后门。
- **7 天有效期**（`RESET_TTL_MS`），过期要重新申请；短密码在这一步被拒（`BAD_PASSWORD`）且**不消耗码**。
- **申请频率**：同一来源 10 分钟最多 5 次（进程内存）—— 防的不是猜码（32^8 ≈ 1.1e12），
  是别让人把 `accounts.json` 当日志刷。

**Tests.** `test/account-reset.test.js`（7）：单元侧（未批 403 / 只存哈希 / 重放 / 覆盖 / 过期 /
短密码不消耗码 / `info` 的 resetPending）与 HTTP 侧（`/account/*`、`/admin/*` 的 404 闸、批准、换发凭证）。

### 35.8 账号面板：改密码要旧密码、改名、退出设备（2026-10-19）

**改密码要旧密码。** §35.6 的 `account.setPassword` 只看会话身份，所以**拿到设备凭证的人**（共用电脑、
被插件读走的 localStorage、导出的备份）可以直接把密码换掉，把主人锁在门外。现在账号**已经有密码**时
必须带 `oldPassword`（`BAD_CREDENTIALS` 拒绝）；第一个密码本来就没有旧密码，所以不要求。改名同理 ——
名字在榜上是公开的，改名的风险是冒充别人。

**退出这台设备 / 踢掉其他设备。** `revokeToken` 与 `revokeAllTokens` 早就写好了，但一直没有入口
（§35.3 写了它们存在）。现在：

| 消息 | 做什么 | 谁受影响 |
|---|---|---|
| `account.logout` | 撤销**当前会话**这张设备凭证 | 只有这台；别的设备照旧（`revokeAllTokens` 的 `exceptHash` 反向用法） |
| `account.revokeOthers` | 撤销**除当前之外**的全部凭证 | 其他设备立刻失效，密码不变 |

会话为此记下 `sha256(这次握手用的凭证)`（`Session.accountTokenHash`，只存哈希、不存明文）——
不然服务端没法把"这一张"和账号的其他凭证区分开。退出之后这台浏览器要重新用密码（或重置码）进来，
所以界面在没有密码时会**警告这是不可逆的**。

**面板本身。** `public/js/ui/account.js` 的 `AccountPanel`：代号 / 注册时间 / 有没有密码 / 已登录设备数，
下面四个动作（改密码、改代号、踢掉其他设备、退出这台设备）；`account.info` 的回复挂在 `ok.account` 上
（`replyAccountOk`），改完就地刷新，不用重连。`ForgotPasswordPanel` 是 §35.7 的两步界面。

**Tests.** `test/account-panel.test.js`（7）：协议收不发、`info` 字段、改名（无密码直接改 / 撞名
`NAME_TAKEN` / 超长在协议层 `BAD_MSG` / 有密码要验 / `accountId` 不变）、`logout` 只撤当前那张、
`revokeOthers` 保留当前那张、没账号的会话四条全拒且不落库。
